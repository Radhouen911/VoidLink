\chapter{Implementation and Security}

\section{Technology Stack Justification}

\subsection{Frontend Technology Choices}

\textbf{React 18 with TypeScript}

React was chosen for the frontend due to its component-based architecture, which naturally separates concerns and enables secure state management. TypeScript adds compile-time type safety, reducing runtime errors in security-critical code.

Justification:
\begin{itemize}
    \item Component isolation prevents state leakage between security contexts
    \item Virtual DOM minimizes direct DOM manipulation vulnerabilities
    \item Large ecosystem provides well-audited cryptographic libraries
    \item TypeScript catches type-related security bugs at compile time
    \item Strong community support for security best practices
\end{itemize}

\textbf{TweetNaCl.js Cryptographic Library}

TweetNaCl.js is a JavaScript port of the NaCl (Networking and Cryptography Library) created by Daniel J. Bernstein. It provides high-security cryptographic primitives with a simple API.

Justification:
\begin{itemize}
    \item Audited implementation of proven cryptographic algorithms
    \item Constant-time operations resist timing attacks
    \item Minimal API surface reduces implementation errors
    \item No external dependencies minimizes supply chain risks
    \item Ed25519 and Curve25519 provide modern elliptic curve cryptography
    \item Authenticated encryption prevents tampering and forgery
\end{itemize}

\textbf{Zustand State Management}

Zustand provides lightweight state management without the complexity of Redux, crucial for maintaining security-critical state.

Justification:
\begin{itemize}
    \item Minimal boilerplate reduces code complexity
    \item Immutable state updates prevent accidental mutations
    \item TypeScript integration ensures type-safe state access
    \item Small bundle size reduces attack surface
    \item Simple API reduces implementation errors
\end{itemize}

\subsection{Backend Technology Choices}

\textbf{Node.js with Express}

Node.js provides a JavaScript runtime for server-side execution, enabling code reuse between frontend and backend for cryptographic operations during testing.

Justification:
\begin{itemize}
    \item Event-driven architecture suits real-time messaging
    \item Non-blocking I/O handles concurrent WebSocket connections efficiently
    \item Express provides minimal, auditable web framework
    \item Large ecosystem of security-focused middleware
    \item Easy integration with WebSocket libraries
\end{itemize}

\textbf{PostgreSQL Database}

PostgreSQL was selected for its robust ACID compliance, advanced features, and security capabilities.

Justification:
\begin{itemize}
    \item ACID transactions ensure data consistency
    \item Row-level security enables fine-grained access control
    \item UUID primary keys prevent enumeration attacks
    \item JSON support for flexible metadata storage
    \item Mature security features (SSL, authentication, encryption at rest)
    \item Stored procedures enable complex queries with single round-trip
\end{itemize}

\textbf{WebSocket (ws library)}

The ws library provides WebSocket server implementation for real-time bidirectional communication.

Justification:
\begin{itemize}
    \item Low-latency message delivery for real-time chat
    \item Persistent connections reduce authentication overhead
    \item Binary frame support for efficient data transfer
    \item Minimal dependencies reduce security risks
    \item Well-maintained with regular security updates
\end{itemize}

\subsection{Cryptographic Primitive Choices}

\textbf{Ed25519 for Digital Signatures}

Ed25519 is a modern elliptic curve signature scheme providing 128-bit security level.

Advantages:
\begin{itemize}
    \item Fast signature generation and verification
    \item Small key and signature sizes (32 and 64 bytes)
    \item Deterministic signatures prevent nonce reuse vulnerabilities
    \item Resistant to side-channel attacks
    \item No patent encumbrances
\end{itemize}

\textbf{Curve25519 for Key Exchange}

Curve25519 is an elliptic curve Diffie-Hellman key exchange algorithm.

Advantages:
\begin{itemize}
    \item Fast key exchange computation
    \item 128-bit security level
    \item Designed to avoid implementation pitfalls
    \item Constant-time implementation resists timing attacks
    \item Compatible with Ed25519 through key conversion
\end{itemize}

\textbf{NaCl box for Message Encryption}

NaCl box combines Curve25519, XSalsa20, and Poly1305 for authenticated encryption.

Advantages:
\begin{itemize}
    \item Authenticated encryption prevents tampering
    \item Fast encryption and decryption
    \item Nonce-based design prevents replay attacks
    \item Integrated key exchange and encryption
    \item Proven security properties
\end{itemize}

\subsection{Authentication Implementation}

\textbf{Account Authentication:}
\begin{enumerate}
    \item Client sends username and password
    \item Server queries database for account
    \item Server verifies password using bcrypt.compare()
    \item Server generates random 64-character hex session token
    \item Server stores session with 24-hour expiration
    \item Server returns session token to client
\end{enumerate}

\textbf{Cryptographic Authentication:}
\begin{enumerate}
    \item Client requests challenge with account session token
    \item Server generates random 32-byte challenge
    \item Server stores challenge with 5-minute expiration
    \item Server returns challenge to client
    \item Client signs challenge with Ed25519 private key
    \item Client sends signed challenge to server
    \item Server retrieves stored challenge and public key
    \item Server verifies signature using TweetNaCl
    \item Server generates crypto session token
    \item Server stores crypto session with 15-minute expiration
    \item Server returns crypto session token to client
\end{enumerate}

\subsection{Message Routing Implementation}

\textbf{Message Sending (REST API):}
\begin{enumerate}
    \item Client encrypts message with recipient's public key
    \item Client sends POST request to /api/messages/send
    \item Server validates both account and crypto sessions
    \item Server validates recipient exists and has crypto profile
    \item Server prevents sending to self
    \item Server stores encrypted payload in messages table
    \item Server returns message ID and timestamp
    \item Server attempts WebSocket delivery if recipient online
    \item Server queues message if recipient offline
\end{enumerate}

\textbf{Real-Time Delivery (WebSocket):}
\begin{enumerate}
    \item Sender's client sends message via WebSocket
    \item Server validates sender's crypto session
    \item Server validates recipient is in sender's contacts
    \item Server stores encrypted message in database
    \item Server checks if recipient is connected
    \item If online, server sends message\_received event to recipient
    \item If offline, server queues message for later delivery
    \item Recipient's client receives and decrypts message
    \item Recipient's client sends delivery confirmation
    \item Server forwards confirmation to sender
\end{enumerate}

\textbf{Offline Message Queue:}
\begin{enumerate}
    \item Message queue service runs every 10 seconds
    \item Service queries message\_queue table for unprocessed messages
    \item Service checks if recipients are now online
    \item For each online recipient, service retrieves queued messages
    \item Service sends messages via WebSocket with fromQueue flag
    \item On successful delivery, service marks queue entry as processed
    \item On failure, service increments retry count
    \item Service cleans up processed entries older than 24 hours
\end{enumerate}

\subsection{Contact Management Implementation}

\textbf{Contact Request Flow:}
\begin{enumerate}
    \item User A sends contact request to User B
    \item Server validates User B exists
    \item Server prevents self-contact requests
    \item Server checks existing relationship status
    \item If no relationship, server creates pending contact entry
    \item If reverse request exists, server auto-accepts (mutual)
    \item Server sends contact\_request\_received event to User B
    \item User B sees request in pending requests list
\end{enumerate}

\textbf{Contact Acceptance Flow:}
\begin{enumerate}
    \item User B accepts contact request
    \item Server updates contact status to "accepted"
    \item Server creates reverse contact relationship
    \item Server sends contact\_accepted event to both users
    \item Both users' contact lists update automatically
    \item Users can now send messages to each other
\end{enumerate}

\textbf{Contact Validation:}
\begin{itemize}
    \item Database function \texttt{are\_contacts()} checks mutual relationship
    \item WebSocket message handlers validate contacts before delivery
    \item Messages to non-contacts are rejected with error
    \item Contact status checked on every message send
\end{itemize}

\subsection{Cryptographic Operations}

\textbf{Key Generation:}
\begin{lstlisting}[language=JavaScript]
export function generateSigningKeyPair(): KeyPair {
  const keyPair = nacl.sign.keyPair();
  return {
    publicKey: toHex(keyPair.publicKey),
    privateKey: toHex(keyPair.secretKey)
  };
}
\end{lstlisting}

\textbf{Private Key Encryption:}
\begin{lstlisting}[language=JavaScript]
export function exportKeysAsBackup(
  privateKey: string, 
  password: string
): string {
  const passwordBytes = stringToBytes(password);
  const nonce = nacl.randomBytes(24);
  const keyHash = nacl.hash(passwordBytes);
  const key = keyHash.slice(0, 32);
  const privateKeyBytes = stringToBytes(privateKey);
  const encrypted = nacl.secretbox(
    privateKeyBytes, nonce, key
  );
  return JSON.stringify({
    version: 1,
    nonce: toBase64(nonce),
    encrypted: toBase64(encrypted),
    timestamp: Date.now()
  });
}
\end{lstlisting}

\textbf{Message Encryption:}
\begin{lstlisting}[language=JavaScript]
export function encryptMessage(
  message: string,
  recipientPublicKey: string,
  senderPrivateKey: string
): string {
  const nonce = nacl.randomBytes(24);
  const messageBytes = stringToBytes(message);
  
  // Convert Ed25519 to Curve25519
  const recipientCurve = ed2curve.convertPublicKey(
    fromHex(recipientPublicKey)
  );
  const senderCurve = ed2curve.convertSecretKey(
    fromHex(senderPrivateKey).slice(0, 32)
  );
  
  const encrypted = nacl.box(
    messageBytes, nonce, 
    recipientCurve, senderCurve
  );
  
  return JSON.stringify({
    nonce: toBase64(nonce),
    encrypted: toBase64(encrypted)
  });
}
\end{lstlisting}

\textbf{Challenge Signing:}
\begin{lstlisting}[language=JavaScript]
export function signChallenge(
  challenge: string, 
  privateKey: string
): string {
  const challengeBytes = fromHex(challenge);
  const privateKeyBytes = fromHex(privateKey);
  const signature = nacl.sign.detached(
    challengeBytes, privateKeyBytes
  );
  return toHex(signature);
}
\end{lstlisting}

\section{Authentication Mechanisms}

\subsection{Password Security}

\textbf{Password Hashing:}
\begin{itemize}
    \item Algorithm: bcrypt with cost factor 12
    \item Salt: Automatically generated per password
    \item Timing: Approximately 250ms per hash (resistant to brute force)
    \item Storage: 60-character hash stored in database
\end{itemize}

\textbf{Password Requirements:}
\begin{itemize}
    \item Minimum length: 8 characters
    \item No complexity requirements (encourages passphrases)
    \item Client-side validation before submission
    \item Server-side validation enforced
\end{itemize}

\subsection{Session Token Security}

\textbf{Token Generation:}
\begin{itemize}
    \item Source: crypto.randomBytes(32) for cryptographic randomness
    \item Format: 64-character hexadecimal string
    \item Uniqueness: Enforced by database unique constraint
    \item Unpredictability: 256 bits of entropy
\end{itemize}

\textbf{Token Storage:}
\begin{itemize}
    \item Client: localStorage for persistence across sessions
    \item Server: PostgreSQL with indexed lookup
    \item Transmission: HTTPS only, never in URL parameters
    \item Expiration: Automatic cleanup of expired tokens
\end{itemize}

\textbf{Token Validation:}
\begin{itemize}
    \item Checked on every API request
    \item Expiration time validated
    \item Associated account status checked
    \item IP address logged for audit
\end{itemize}

\subsection{Challenge-Response Authentication}

\textbf{Challenge Generation:}
\begin{itemize}
    \item Random 32-byte value using crypto.randomBytes()
    \item Stored in database with 5-minute expiration
    \item Linked to specific account session and crypto profile
    \item Single-use: marked as used after verification
\end{itemize}

\textbf{Signature Verification:}
\begin{lstlisting}[language=JavaScript]
const verifySignature = (
  message, signature, publicKey
) => {
  const messageBytes = Buffer.from(message, 'hex');
  const signatureBytes = Buffer.from(signature, 'hex');
  const publicKeyBytes = fromHex(publicKey);
  
  return nacl.sign.detached.verify(
    messageBytes,
    signatureBytes,
    publicKeyBytes
  );
};
\end{lstlisting}

\textbf{Security Properties:}
\begin{itemize}
    \item Proves possession of private key without revealing it
    \item Challenge randomness prevents replay attacks
    \item Expiration limits attack window
    \item Single-use prevents challenge reuse
    \item Signature verification uses constant-time operations
\end{itemize}

\section{Cryptographic Design and Key Management}

\subsection{Key Lifecycle}

\textbf{Key Generation:}
\begin{enumerate}
    \item User provides passphrase during registration
    \item Client generates Ed25519 key pair using TweetNaCl
    \item Public key: 32 bytes (64 hex characters)
    \item Private key: 64 bytes (128 hex characters)
    \item Keys generated with cryptographically secure random number generator
\end{enumerate}

\textbf{Key Storage:}
\begin{enumerate}
    \item Private key encrypted with passphrase using NaCl secretbox
    \item Encrypted private key stored in browser localStorage
    \item Encrypted backup uploaded to server (optional)
    \item Public key stored on server for distribution
    \item Private key cached in memory during active session
\end{enumerate}

\textbf{Key Usage:}
\begin{enumerate}
    \item Private key decrypted with passphrase when needed
    \item Used for signing authentication challenges
    \item Converted to Curve25519 for message encryption/decryption
    \item Never transmitted to server in any form
    \item Cleared from memory on logout
\end{enumerate}

\textbf{Key Backup and Recovery:}
\begin{enumerate}
    \item User enables cloud backup during registration
    \item Client encrypts private key with passphrase
    \item Encrypted key uploaded to server
    \item On new device, user logs in with credentials and passphrase
    \item Client downloads encrypted backup from server
    \item Client decrypts with passphrase
    \item Keys restored to new device
\end{enumerate}

\subsection{Key Derivation}

VoidLink uses Ed25519 keys for signing and derives Curve25519 keys for encryption:

\textbf{Ed25519 to Curve25519 Conversion:}
\begin{itemize}
    \item Ed25519 public key (32 bytes) → Curve25519 public key (32 bytes)
    \item Ed25519 private key seed (32 bytes) → Curve25519 private key (32 bytes)
    \item Conversion performed using ed2curve library
    \item Mathematically related curves enable key reuse
    \item Single key pair serves both signing and encryption
\end{itemize}

\textbf{Benefits:}
\begin{itemize}
    \item Simplified key management (one key pair per user)
    \item Reduced storage requirements
    \item Consistent security level across operations
    \item Proven mathematical relationship between curves
\end{itemize}

\subsection{Passphrase Security}

\textbf{Passphrase Requirements:}
\begin{itemize}
    \item Separate from account password
    \item Used only for private key encryption
    \item Never transmitted to server
    \item Stored in sessionStorage during active session
    \item Cleared on tab close
\end{itemize}

\textbf{Key Derivation from Passphrase:}
\begin{lstlisting}[language=JavaScript]
const passwordBytes = stringToBytes(password);
const keyHash = nacl.hash(passwordBytes);
const key = keyHash.slice(0, 32);
\end{lstlisting}

\textbf{Security Considerations:}
\begin{itemize}
    \item SHA-512 hash provides 256-bit key
    \item No salt used (deterministic for same passphrase)
    \item Weak passphrases remain vulnerable to brute force
    \item User education critical for strong passphrase selection
\end{itemize}

\section{End-to-End Encryption Workflow}

\subsection{Encryption Process Detail}

\textbf{Step 1: Key Preparation}
\begin{enumerate}
    \item Retrieve recipient's Ed25519 public key from contact list
    \item Retrieve sender's Ed25519 private key from session memory
    \item Convert both keys to Curve25519 format using ed2curve
    \item Sender's private key: Extract 32-byte seed, convert to Curve25519
    \item Recipient's public key: Convert directly to Curve25519
\end{enumerate}

\textbf{Step 2: Encryption}
\begin{enumerate}
    \item Generate random 24-byte nonce
    \item Convert message string to UTF-8 bytes
    \item Compute shared secret using ECDH (Curve25519)
    \item Encrypt message with XSalsa20 stream cipher
    \item Compute Poly1305 authentication tag
    \item Combine ciphertext and authentication tag
\end{enumerate}

\textbf{Step 3: Payload Construction}
\begin{enumerate}
    \item Encode nonce as base64
    \item Encode encrypted data as base64
    \item Create JSON object: \{nonce, encrypted\}
    \item Serialize to string for transmission
\end{enumerate}

\subsection{Decryption Process Detail}

\textbf{Step 1: Payload Parsing}
\begin{enumerate}
    \item Parse JSON payload string
    \item Decode base64 nonce to bytes
    \item Decode base64 encrypted data to bytes
    \item Validate payload structure
\end{enumerate}

\textbf{Step 2: Key Preparation}
\begin{enumerate}
    \item Retrieve sender's Ed25519 public key
    \item Retrieve recipient's Ed25519 private key from session
    \item Convert both keys to Curve25519 format
    \item Recipient's private key: Extract seed, convert
    \item Sender's public key: Convert directly
\end{enumerate}

\textbf{Step 3: Decryption}
\begin{enumerate}
    \item Compute shared secret using ECDH
    \item Verify Poly1305 authentication tag
    \item If verification fails, return null (tampering detected)
    \item Decrypt ciphertext with XSalsa20
    \item Convert decrypted bytes to UTF-8 string
    \item Return plaintext message
\end{enumerate}

\subsection{Cryptographic Properties}

\textbf{Confidentiality:}
\begin{itemize}
    \item XSalsa20 stream cipher with 256-bit key
    \item Nonce ensures unique keystream per message
    \item Shared secret derived from ECDH key exchange
    \item Only sender and recipient can decrypt
\end{itemize}

\textbf{Authenticity:}
\begin{itemize}
    \item Poly1305 MAC authenticates ciphertext
    \item Prevents tampering and forgery
    \item Verifies message came from claimed sender
    \item Detects any modification of encrypted data
\end{itemize}

\textbf{Forward Secrecy:}
\begin{itemize}
    \item Not implemented in current version
    \item Static key pairs used for all messages
    \item Compromise of private key exposes all past messages
    \item Future enhancement: Implement Double Ratchet algorithm
\end{itemize}

\section{Security Guarantees and Threat Considerations}

\subsection{Security Guarantees}

\textbf{Server Cannot Decrypt Messages:}
\begin{itemize}
    \item Server never receives private keys
    \item Server stores only encrypted payloads
    \item Encryption performed entirely client-side
    \item Mathematical guarantee based on cryptographic hardness
\end{itemize}

\textbf{Server Cannot Impersonate Users:}
\begin{itemize}
    \item Challenge-response proves key possession
    \item Server cannot forge signatures without private key
    \item Each message operation requires valid crypto session
    \item Crypto session requires successful challenge verification
\end{itemize}

\textbf{Messages Cannot Be Tampered:}
\begin{itemize}
    \item Poly1305 MAC detects any modification
    \item Authenticated encryption prevents forgery
    \item Tampering causes decryption to fail
    \item No partial decryption of modified messages
\end{itemize}

\textbf{Replay Attacks Prevented:}
\begin{itemize}
    \item Unique nonce for each message
    \item Challenges expire after 5 minutes
    \item Challenges marked as used after verification
    \item Session tokens expire automatically
\end{itemize}

\subsection{Threat Model}

\textbf{Threats Within Scope:}

\textit{Malicious Server Operator:}
\begin{itemize}
    \item Threat: Server operator attempts to read messages
    \item Mitigation: End-to-end encryption prevents access
    \item Residual Risk: Metadata exposure (who, when, frequency)
\end{itemize}

\textit{Database Breach:}
\begin{itemize}
    \item Threat: Attacker gains access to database
    \item Mitigation: All messages stored encrypted
    \item Residual Risk: Encrypted private key backups vulnerable to brute force
\end{itemize}

\textit{Network Eavesdropping:}
\begin{itemize}
    \item Threat: Attacker intercepts network traffic
    \item Mitigation: HTTPS encrypts transport layer
    \item Residual Risk: TLS vulnerabilities or certificate attacks
\end{itemize}

\textit{Man-in-the-Middle During Key Exchange:}
\begin{itemize}
    \item Threat: Attacker substitutes public keys
    \item Mitigation: Key fingerprint verification
    \item Residual Risk: Users must manually verify fingerprints
\end{itemize}

\textbf{Threats Outside Scope:}

\textit{Compromised Client Device:}
\begin{itemize}
    \item Malware on user's device can access private keys in memory
    \item Keyloggers can capture passphrases
    \item No client-side protection against device compromise
\end{itemize}

\textit{Physical Access:}
\begin{itemize}
    \item Attacker with physical access to unlocked device
    \item Can access localStorage and session data
    \item Device-level security is user's responsibility
\end{itemize}

\textit{Coercion:}
\begin{itemize}
    \item User forced to decrypt messages or reveal passphrase
    \item No technical protection against coercion
    \item Plausible deniability not implemented
\end{itemize}

\textit{Metadata Analysis:}
\begin{itemize}
    \item Server logs communication patterns
    \item Timing and frequency analysis possible
    \item No protection against traffic analysis
\end{itemize}

\subsection{Security Limitations}

\textbf{No Forward Secrecy:}
\begin{itemize}
    \item Static key pairs used for all messages
    \item Compromise of private key exposes all past messages
    \item Future enhancement required: Implement ephemeral keys
\end{itemize}

\textbf{Weak Passphrase Vulnerability:}
\begin{itemize}
    \item Encrypted private key backups vulnerable to brute force
    \item No key stretching (PBKDF2, Argon2) implemented
    \item User education critical but insufficient
\end{itemize}

\textbf{No Key Verification Enforcement:}
\begin{itemize}
    \item Users can verify key fingerprints manually
    \item No enforcement of verification before messaging
    \item Vulnerable to key substitution attacks
\end{itemize}

\textbf{Metadata Exposure:}
\begin{itemize}
    \item Server knows who communicates with whom
    \item Message timing and frequency visible
    \item No protection against traffic analysis
\end{itemize}

\textbf{No Multi-Device Synchronization:}
\begin{itemize}
    \item Each device requires separate login
    \item Message history not synchronized across devices
    \item Deliberate limitation to maintain security simplicity
\end{itemize}

\subsection{Security Best Practices Implemented}

\textbf{Defense in Depth:}
\begin{itemize}
    \item Multiple independent security layers
    \item Account authentication + cryptographic authentication
    \item Transport encryption (HTTPS) + end-to-end encryption
    \item Session expiration + challenge expiration
\end{itemize}

\textbf{Principle of Least Privilege:}
\begin{itemize}
    \item Server has minimal necessary permissions
    \item Database functions restrict data access
    \item Middleware validates permissions per request
    \item Cascading deletes maintain data consistency
\end{itemize}

\textbf{Secure Defaults:}
\begin{itemize}
    \item HTTPS required for all communication
    \item Helmet.js security headers enabled
    \item CORS restricted to known origins
    \item Rate limiting on authentication endpoints
\end{itemize}

\textbf{Audit Logging:}
\begin{itemize}
    \item All authentication events logged
    \item Failed login attempts recorded
    \item Message operations audited
    \item IP addresses and timestamps captured
\end{itemize}

\textbf{Input Validation:}
\begin{itemize}
    \item Username format validation
    \item Password length requirements
    \item Public key format verification
    \item SQL injection prevention (parameterized queries)
\end{itemize}
