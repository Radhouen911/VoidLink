\chapter*{Abstract}
\addcontentsline{toc}{chapter}{Abstract}

This report presents the design, implementation, and evaluation of VoidLink, a zero-trust secure messaging system that implements end-to-end encryption with cryptographic authentication. VoidLink employs a two-layer security architecture that separates traditional account management from cryptographic operations, ensuring that even with server compromise, private keys remain encrypted and unusable without the user's passphrase. The system uses Ed25519 for digital signatures and Curve25519 for asymmetric encryption, implemented through the TweetNaCl library. A WebSocket-based real-time messaging infrastructure provides instant message delivery with automatic queuing for offline users. This project demonstrates the feasibility of building privacy-preserving communication systems where trust boundaries are clearly defined and enforced through cryptographic protocols rather than service provider promises.

\chapter{General Context and Objectives}
\label{ch:context}

\section{Background and Motivation}

The proliferation of digital communication platforms has fundamentally transformed how individuals and organizations exchange information. However, this transformation has been accompanied by growing concerns about privacy, data security, and the extent of surveillance capabilities that service providers possess. Traditional messaging systems typically operate under a trust-based model where users must rely on service providers to protect their communications, often with limited transparency into actual security practices.

Modern security breaches and government surveillance programs have demonstrated that relying solely on service provider promises is insufficient for protecting sensitive communications. The need for cryptographic guarantees rather than policy-based assurances has become increasingly evident. End-to-end encryption has emerged as a critical technology for addressing these concerns, ensuring that messages can only be decrypted by their intended recipients, even if the service provider's infrastructure is compromised.

The zero-trust security model represents a paradigm shift from traditional perimeter-based security. In a zero-trust architecture, no component of the system is inherently trusted, and every operation must be verified and authorized. This approach is particularly relevant for messaging systems, where the service provider should be treated as a potential adversary, and security guarantees must be mathematically verifiable rather than policy-dependent.

\section{Problem Statement}

Existing messaging platforms exhibit several critical limitations that undermine user privacy and security:

\begin{itemize}
\item \textbf{Server-side visibility:} Most messaging systems allow service providers to access message contents, either in plaintext or through escrow keys that can be used to decrypt messages.
\item \textbf{Centralized key management:} Private keys are often managed by service providers or stored in ways that enable access by third parties, creating single points of failure.
\item \textbf{Authentication weaknesses:} Traditional password-based authentication provides limited security guarantees and is vulnerable to various attack vectors including phishing and credential theft.
\item \textbf{Metadata exposure:} Even when message contents are encrypted, metadata about communications (who is talking to whom, when, frequency) is often accessible to service providers and can reveal sensitive information patterns.
\item \textbf{Insufficient transparency:} Users typically cannot verify security claims independently and must trust that service providers implement security measures correctly.
\end{itemize}

These limitations create a fundamental trust asymmetry where users must place significant trust in service providers without cryptographic guarantees. This project addresses these challenges by designing and implementing a messaging system where privacy is mathematically enforced rather than policy-dependent.

\section{Project Objectives}

The primary objective of this project is to design, implement, and evaluate a zero-trust secure messaging system that demonstrates the feasibility of privacy-preserving communication with minimal trust requirements. Specific objectives include:

\begin{enumerate}
\item \textbf{Design a two-layer security architecture} that separates account management from cryptographic operations, ensuring that even if one layer is compromised, the other remains secure.
\item \textbf{Implement end-to-end encryption} where all cryptographic operations occur client-side, and the server never has access to decryption keys or plaintext message contents.
\item \textbf{Develop a cryptographic authentication mechanism} using challenge-response protocols that eliminate the need for traditional password-based authentication for message operations.
\item \textbf{Create a real-time messaging infrastructure} that provides instant message delivery while maintaining security guarantees through WebSocket technology.
\item \textbf{Design and implement a contact management system} that enables secure discovery and verification of communication partners.
\item \textbf{Build a production-ready prototype} that demonstrates the complete workflow from user registration through secure message exchange.
\end{enumerate}

\section{Scope and Limitations}

This project focuses on building a secure messaging system for one-on-one conversations. The scope explicitly excludes several features that are common in commercial messaging platforms:

\begin{itemize}
\item \textbf{Group messaging:} Multi-party conversations introduce additional cryptographic complexity related to key management and forward secrecy that are outside the scope of this project.
\item \textbf{File transfer:} While the backend architecture supports file transfer conceptually through message types, the current frontend implementation focuses on text messaging only. File transfer remains a planned feature for future expansion.
\item \textbf{Group messaging:} Multi-party conversations introduce additional cryptographic complexity related to key management and forward secrecy that are outside the scope of this project.
\item \textbf{Social features:} No public profiles, feeds, or social networking capabilities are included, as the focus is purely on private communication.
\item \textbf{Mobile applications:} The implementation is web-based only, focusing on browser-based clients rather than native mobile applications.
\end{itemize}

The system is designed to protect against certain threat models while explicitly acknowledging limitations:

\textbf{Protected against:}
\begin{itemize}
\item Server compromise and data breaches
\item Malicious or curious service providers
\item Network eavesdropping and man-in-the-middle attacks
\item Database compromise (encrypted data only)
\item Basic cross-site scripting attacks
\end{itemize}

\textbf{Not protected against:}
\begin{itemize}
\item Compromised user devices or malware
\item Physical access to user devices
\item Coercion attacks (e.g., forcing users to reveal keys)
\item Advanced persistent threats that compromise client-side execution
\item Traffic analysis that reveals communication patterns from metadata
\end{itemize}

\section{Brief Presentation of the Proposed Solution}

VoidLink is a zero-trust secure messaging system that implements end-to-end encryption with cryptographic authentication. The system architecture separates concerns into three distinct layers:

\textbf{Layer 1: Account Management} provides traditional username-password authentication for account access and management operations. This layer handles registration, login, session management, and account-level settings.

\textbf{Layer 2: Cryptographic Operations} implements a challenge-response authentication system using Ed25519 digital signatures. Users must cryptographically prove possession of their private keys to perform message operations, eliminating password-based authentication for messaging activities. Additionally, users provide a passphrase during registration that encrypts their private keys for secure storage and multi-device synchronization through optional cloud backup.

\textbf{Layer 3: Application Operations} handles messaging, contact management, and real-time communication. All message contents are encrypted client-side using Curve25519 public-key encryption before transmission, ensuring that the server only handles opaque encrypted blobs.

The system uses the TweetNaCl cryptographic library, which implements the NaCl (Networking and Cryptography Library) API. Ed25519 is used for digital signatures and authentication challenges, while Curve25519 (accessed through the ed2curve library) provides public-key encryption for message contents. All cryptographic operations occur in the client's browser before data is transmitted to the server.

A WebSocket-based infrastructure provides real-time bidirectional communication, enabling instant message delivery, typing indicators, delivery confirmations, and presence updates. A message queue system ensures that messages are delivered to users even when they are temporarily offline.

The server is designed with a zero-trust philosophy where it never accesses private keys or decryption capabilities. The database stores only encrypted payloads and metadata necessary for routing, with no ability to decrypt message contents even with full database access.

\chapter{Functional Requirements and Analysis}
\label{ch:requirements}

\section{Functional Requirements}

Functional requirements define the specific behaviors and capabilities that the system must provide. These requirements are organized by user roles and system components.

\subsection{User Account Management}

\textbf{FR-001: User Registration}
\begin{itemize}
\item The system must allow new users to create accounts by providing a unique username, password, and passphrase.
\item Username must be between 3 and 50 characters and contain only alphanumeric characters, underscores, and hyphens.
\item Password must be at least 8 characters long.
\item Passphrase is required to encrypt the private key for secure storage and cloud backup.
\item The system must reject duplicate usernames.
\item Account creation must be logged in the audit system.
\end{itemize}

\textbf{FR-002: User Authentication}
\begin{itemize}
\item The system must authenticate users using username and password.
\item Successful authentication must create an account session with 24-hour validity.
\item The system must reject invalid credentials and log failed login attempts.
\item Account sessions must track IP addresses and user agents for security monitoring.
\end{itemize}

\textbf{FR-003: Session Management}
\begin{itemize}
\item The system must validate account sessions for all account management operations.
\item Sessions must expire after 24 hours of inactivity or absolute time expiration.
\item The system must allow users to explicitly log out, invalidating their sessions.
\item Active sessions must be queryable and revocable.
\end{itemize}

\subsection{Cryptographic Profile Management}

\textbf{FR-004: Public Key Upload}
\begin{itemize}
\item Users must be able to upload their Ed25519 public key to establish their cryptographic identity.
\item Each account can have exactly one cryptographic profile.
\item Public keys must be validated for format (64-character hexadecimal string).
\item Key upload must be logged in the audit system.
\end{itemize}

\textbf{FR-005: Private Key Backup}
\begin{itemize}
\item Users must be able to enable cloud backup of their encrypted private keys.
\item Private keys must be encrypted client-side before transmission to the server.
\item The server must store only encrypted private key backups without decryption capability.
\item Users must be able to retrieve their encrypted private key backups using account authentication.
\item Users must be able to disable cloud backup, which removes encrypted backups from the server.
\end{itemize}

\textbf{FR-006: Cryptographic Authentication}
\begin{itemize}
\item The system must issue cryptographic challenges to users requesting message operations.
\item Challenges must be random 64-character hexadecimal strings valid for 5 minutes.
\item Users must sign challenges using their Ed25519 private keys.
\item The system must verify signatures using stored public keys.
\item Successful verification must create a cryptographic session valid for 24 hours.
\item Failed authentication attempts must be logged in the audit system.
\end{itemize}

\subsection{Contact Management}

\textbf{FR-007: User Discovery}
\begin{itemize}
\item Users must be able to search for other users by username.
\item User discovery must return public keys associated with usernames.
\item Only users with cryptographic profiles must be discoverable.
\item User discovery must require account session authentication.
\end{itemize}

\textbf{FR-008: Contact Requests}
\begin{itemize}
\item Users must be able to send contact requests to other users.
\item Contact requests can include an optional message.
\item Users must be able to accept or reject incoming contact requests.
\item The system must prevent duplicate contact requests and self-contacts.
\item Contact request status must be queryable.
\end{itemize}

\textbf{FR-009: Contact List}
\begin{itemize}
\item Users must be able to view their list of accepted contacts.
\item Contact list must include usernames, public keys, and presence information.
\item Users must be able to remove contacts from their list.
\item Contact relationships must be bidirectional (mutual contacts).
\end{itemize}

\subsection{Messaging Operations}

\textbf{FR-010: Message Sending}
\begin{itemize}
\item Users must be able to send encrypted messages to their contacts.
\item Messages must be encrypted client-side before transmission.
\item The server must store encrypted messages without decryption capability.
\item Message sending requires both account and cryptographic sessions.
\item The system must prevent sending messages to non-contacts.
\item The system must prevent sending messages to oneself.
\end{itemize}

\textbf{FR-011: Message Reception}
\begin{itemize}
\item Users must be able to receive messages in real-time when online.
\item Offline users must receive messages through a queue system.
\item Messages must be delivered automatically when users come online.
\item Users must be able to query their inbox with pagination support.
\item Message delivery confirmations must be provided to senders.
\end{itemize}

\textbf{FR-012: Message History}
\begin{itemize}
\item Users must be able to view conversation history with specific contacts.
\item Conversation history must support pagination and filtering by timestamp.
\item Message history must preserve chronological ordering.
\item Users must be able to delete messages (soft delete).
\end{itemize}

\textbf{FR-013: Real-time Features}
\begin{itemize}
\item The system must provide typing indicators between contacts.
\item The system must provide delivery confirmations for sent messages.
\item The system must provide presence updates (online/offline status).
\item All real-time features must use WebSocket connections.
\end{itemize}

\section{Use-Case Descriptions}

This section describes key use cases that illustrate system behavior from the user's perspective.

\subsection{Use Case 1: User Registration and Initialization}

\textbf{Primary Actor:} New User

\textbf{Preconditions:} User has a web browser with JavaScript enabled.

\textbf{Main Success Scenario:}
\begin{enumerate}
\item User navigates to the registration page.
\item User enters username, password, and passphrase meeting format requirements.
\item System validates username uniqueness, password strength, and passphrase requirements.
\item System creates account with hashed password.
\item System generates cryptographic key pair in user's browser (Ed25519).
\item User uploads public key to the server.
\item System creates cryptographic profile linked to account.
\item User optionally enables cloud backup of encrypted private key.
\item System confirms successful registration and initialization.
\end{enumerate}

\textbf{Alternative Flows:}
\begin{itemize}
\item If username already exists, system displays error message and user must choose different username.
\item If password is too weak, system displays requirements and user must enter stronger password.
\item If key generation fails, user can retry key generation.
\end{itemize}

\subsection{Use Case 2: User Login and Message Authentication}

\textbf{Primary Actor:} Registered User

\textbf{Preconditions:} User has registered account and cryptographic profile.

\textbf{Main Success Scenario:}
\begin{enumerate}
\item User navigates to login page and enters username and password.
\item System validates credentials and creates account session.
\item User enters passphrase to decrypt private key stored locally or retrieved from cloud backup.
\item User requests cryptographic challenge from server.
\item Server generates random challenge and stores it with expiration.
\item User signs challenge with decrypted private key in browser.
\item User sends signed challenge to server.
\item Server verifies signature using stored public key.
\item System creates cryptographic session.
\item User can now send and receive messages.
\end{enumerate}

\textbf{Alternative Flows:}
\begin{itemize}
\item If credentials are invalid, system rejects login and logs failed attempt.
\item If cryptographic signature verification fails, system rejects authentication and logs attempt.
\item If challenge expires before verification, user must request new challenge.
\end{itemize}

\subsection{Use Case 3: Secure Message Exchange}

\textbf{Primary Actor:} Registered User

\textbf{Preconditions:} User has active account and cryptographic sessions. User has contacts in contact list.

\textbf{Main Success Scenario:}
\begin{enumerate}
\item User selects contact from contact list.
\item User types message in chat interface.
\item Client encrypts message using recipient's public key (Curve25519).
\item Client sends encrypted payload to server via WebSocket.
\item Server validates that sender and recipient are contacts.
\item Server stores encrypted message in database.
\item If recipient is online, server delivers message via WebSocket immediately.
\item If recipient is offline, server queues message for later delivery.
\item Recipient receives encrypted message and decrypts using private key.
\item Recipient confirms delivery, which is sent back to sender.
\end{enumerate}

\textbf{Alternative Flows:}
\begin{itemize}
\item If recipient is not in contact list, system rejects message sending.
\item If recipient is offline, message is queued and delivered when recipient comes online.
\item If decryption fails, recipient reports error but message remains in database.
\end{itemize}

\subsection{Use Case 4: Contact Management}

\textbf{Primary Actor:} Registered User

\textbf{Preconditions:} User has active account and cryptographic sessions.

\textbf{Main Success Scenario:}
\begin{enumerate}
\item User searches for another user by username.
\item System returns user's public key if user exists and has cryptographic profile.
\item User sends contact request to discovered user.
\item System creates pending contact request.
\item Target user receives contact request notification.
\item Target user accepts or rejects request.
\item If accepted, mutual contact relationship is established.
\item Both users can now send messages to each other.
\end{enumerate}

\textbf{Alternative Flows:}
\begin{itemize}
\item If user not found, system returns error message.
\item If contact request already exists, system indicates current status.
\item If target user rejects request, relationship is not established.
\end{itemize}

\section{Constraints and Assumptions}

\subsection{Technical Constraints}

\begin{itemize}
\item \textbf{Browser compatibility:} The system requires modern browsers with WebSocket and Web Crypto API support. Legacy browsers are not supported.
\item \textbf{JavaScript requirement:} All cryptographic operations occur client-side, requiring JavaScript to be enabled. The system cannot function without client-side JavaScript.
\item \textbf{Network dependency:} The system requires stable internet connectivity for real-time messaging. Offline functionality is limited to message queuing.
\item \textbf{Server infrastructure:} The system requires a PostgreSQL database and Node.js runtime environment.
\end{itemize}

\subsection{Design Constraints}

\begin{itemize}
\item \textbf{Zero-trust principle:} The server must never access private keys or decrypt message contents. This constraint affects all server-side design decisions.
\item \textbf{Two-layer authentication:} Account operations and cryptographic operations must be separated, requiring two independent authentication mechanisms.
\item \textbf{WebSocket dependency:} Real-time features require WebSocket connections, limiting support to HTTP/HTTPS environments.
\item \textbf{Cryptographic library dependency:} The system depends on TweetNaCl library for all cryptographic operations, limiting cryptographic algorithm choices.
\end{itemize}

\subsection{Assumptions}

\begin{itemize}
\item \textbf{User device security:} The system assumes that user devices are not compromised. Malware or compromised devices can access private keys stored in browser storage.
\item \textbf{Network trust:} The system assumes that cryptographic keys are correctly distributed. It does not protect against initial key exchange attacks (out-of-band verification required).
\item \textbf{Browser security:} The system assumes that browsers correctly implement Web Crypto API and are not compromised. Browser vulnerabilities can affect system security.
\item \textbf{Server availability:} The system assumes reasonable server uptime. Extended downtime affects message delivery for offline users.
\item \textbf{User behavior:} The system assumes users follow security best practices (e.g., not sharing private keys, using strong passwords).
\end{itemize}

\chapter{System Architecture and Design}
\label{ch:architecture}

\section{Global Architecture}

The VoidLink system follows a three-tier architecture consisting of a client layer (web browser), an application server layer (Node.js), and a data persistence layer (PostgreSQL). Communication between these layers uses HTTP/REST for synchronous operations and WebSocket for real-time bidirectional communication.

\subsection{Client Layer (Frontend)}

The client layer is implemented as a single-page web application using React and TypeScript. All cryptographic operations occur within the browser using the TweetNaCl JavaScript library. The client is responsible for:

\begin{itemize}
\item User interface rendering and user interaction handling
\item Cryptographic key generation, storage, and management
\item Message encryption and decryption
\item Digital signature creation and verification
\item WebSocket connection management for real-time communication
\item Local storage of encrypted private keys
\end{itemize}

The client communicates with the server through RESTful HTTP endpoints for account management and cryptographic operations, and maintains a persistent WebSocket connection for real-time messaging.

\subsection{Application Server Layer (Backend)}

The application server is implemented using Node.js with the Express framework. The server provides:

\begin{itemize}
\item REST API endpoints for account management, user discovery, and message retrieval
\item WebSocket server for real-time message delivery
\item Session management for both account and cryptographic sessions
\item Message queue service for offline message delivery
\item Connection management for WebSocket clients
\item Request validation and authentication middleware
\item Audit logging for security events
\end{itemize}

The server is designed with a zero-trust philosophy: it never accesses private keys, never decrypts message contents, and treats all cryptographic payloads as opaque data blobs.

\subsection{Data Persistence Layer (Database)}

The database layer uses PostgreSQL to store:

\begin{itemize}
\item User accounts and password hashes
\item Account and cryptographic session tokens
\item Cryptographic challenges and their states
\item Cryptographic profiles (public keys only)
\item Encrypted message payloads
\item Contact relationships
\item User presence information
\item Message queue for offline delivery
\item Audit logs for security events
\end{itemize}

The database schema is designed to support referential integrity, cascading deletes, and efficient querying with appropriate indexes.

\section{Communication Flows}

This section describes the primary communication patterns between system components.

\subsection{Account Registration and Initialization Flow}

When a new user registers, the following sequence occurs:

\begin{enumerate}
\item Client sends registration request (username, password) via HTTP POST to \texttt{/api/auth/register}
\item Server validates username format and uniqueness, password strength
\item Server hashes password using bcrypt and creates account record
\item Server returns account ID and username to client
\item Client generates Ed25519 key pair using TweetNaCl
\item Client encrypts private key with user-provided passphrase
\item Client stores encrypted private key in browser's sessionStorage
\item Client uploads public key to server via HTTP POST to \texttt{/api/auth/crypto/upload-key}
\item Server creates cryptographic profile linked to account
\item Client optionally enables cloud backup by sending encrypted private key to server
\end{enumerate}

\subsection{Cryptographic Authentication Flow}

Before users can send messages, they must establish a cryptographic session:

\begin{enumerate}
\item User logs in with username and password, receiving account session token
\item Client requests cryptographic challenge via HTTP POST to \texttt{/api/auth/crypto/challenge}
\item Server generates random 64-character hex challenge, stores it with 5-minute expiration
\item Client signs challenge using Ed25519 private key
\item Client sends signed challenge to server via HTTP POST to \texttt{/api/auth/crypto/verify}
\item Server retrieves challenge and validates it has not expired or been used
\item Server verifies signature using stored public key via TweetNaCl
\item Server creates cryptographic session token valid for 24 hours
\item Client stores both account and cryptographic session tokens
\end{enumerate}

\subsection{Message Sending Flow}

The message sending process ensures end-to-end encryption:

\begin{enumerate}
\item User selects contact and types message in client interface
\item Client retrieves recipient's public key (obtained during contact establishment)
\item Client converts recipient's Ed25519 public key to Curve25519 using ed2curve library
\item Client converts own Ed25519 private key to Curve25519 secret key
\item Client generates random nonce and encrypts message using NaCl box (Curve25519)
\item Client sends encrypted payload to server via WebSocket or HTTP POST to \texttt{/api/messages/send}
\item Server validates sender and recipient are contacts
\item Server stores encrypted payload in database with sender and recipient identifiers
\item If recipient is online, server immediately delivers via WebSocket
\item If recipient is offline, server queues message in message\_queue table
\item Message queue service periodically checks for offline users coming online
\item When recipient comes online, queued messages are delivered via WebSocket
\item Recipient's client receives encrypted payload and decrypts using Curve25519
\end{enumerate}

\subsection{WebSocket Connection Flow}

Real-time features require WebSocket connections with two-layer authentication:

\begin{enumerate}
\item Client initiates WebSocket connection with account and crypto session tokens as query parameters
\item Server validates both tokens before accepting connection
\item Server verifies tokens are not expired and belong to same account
\item Server adds connection to connection manager with user context
\item Server updates user presence to online
\item Server notifies user's contacts about online status
\item Server sends welcome message with connection confirmation
\item Message queue service checks for queued messages and delivers them
\item Client and server maintain connection with periodic ping/pong messages
\item When connection closes, server updates presence and notifies contacts
\end{enumerate}

\section{Security Design}

The security architecture is based on defense-in-depth principles with multiple layers of protection.

\subsection{Zero-Trust Server Design}

The server operates under a zero-trust model where it assumes it may be compromised at any time. Key design principles include:

\begin{itemize}
\item \textbf{No private key access:} Private keys never leave the client browser (except in encrypted backups that the server cannot decrypt)
\item \textbf{Opaque payload handling:} The server treats all encrypted message payloads as opaque binary data without attempting to interpret or validate contents
\item \textbf{Minimal metadata storage:} The server stores only metadata necessary for routing (sender ID, recipient ID, timestamp) without message content
\item \textbf{Cryptographic session separation:} Cryptographic sessions are independent from account sessions, limiting attack surface
\item \textbf{Challenge binding:} Cryptographic challenges are bound to specific crypto profiles and account sessions, preventing replay attacks
\end{itemize}

\subsection{Two-Layer Authentication Architecture}

The system implements a two-layer authentication model that separates concerns:

\textbf{Layer 1: Account Authentication}
\begin{itemize}
\item Purpose: Account access and management operations
\item Method: Username and password with bcrypt hashing
\item Session duration: 24 hours
\item Scope: Account settings, key upload, backup management
\item Protection: Standard password-based security with bcrypt work factor of 12
\end{itemize}

\textbf{Layer 2: Cryptographic Authentication}
\begin{itemize}
\item Purpose: Cryptographic operations and messaging
\item Method: Ed25519 challenge-response signature verification
\item Session duration: 24 hours (same as account sessions)
\item Scope: Message sending/receiving, contact operations
\item Protection: Cryptographic proof of private key possession, immune to password theft
\end{itemize}

This separation ensures that even if an account password is compromised, attackers cannot send messages without access to the private key. Conversely, even if a cryptographic session is compromised, it cannot be used to access account settings or change passwords.

\subsection{Key Management and Storage}

Key management follows best practices for client-side cryptographic operations:

\begin{itemize}
\item \textbf{Key generation:} Keys are generated in the browser using cryptographically secure random number generation (TweetNaCl's randomBytes)
\item \textbf{Private key storage:} Private keys are encrypted with a user-provided passphrase before storage in browser sessionStorage
\item \textbf{Cloud backup:} Optional cloud backup stores passphrase-encrypted private keys, allowing recovery across devices (if user remembers passphrase)
\item \textbf{Key derivation:} Encryption passphrase is hashed using SHA-256 to derive encryption key for private key backup
\item \textbf{No key escrow:} The server never has access to unencrypted private keys or passphrases
\end{itemize}

\subsection{Message Encryption}

Messages are encrypted using Curve25519 public-key cryptography through NaCl box primitive:

\begin{itemize}
\item \textbf{Algorithm:} X25519 (Curve25519) key exchange with ChaCha20-Poly1305 authenticated encryption
\item \textbf{Key conversion:} Ed25519 signing keys are converted to Curve25519 encryption keys using ed2curve library
\item \textbf{Nonce generation:} Random 24-byte nonces are generated for each message
\item \textbf{Authenticated encryption:} NaCl box provides authenticated encryption ensuring both confidentiality and integrity
\item \textbf{Forward secrecy consideration:} While not implemented in this version, the architecture supports future implementation of forward secrecy through ephemeral keys
\end{itemize}

\subsection{Contact Verification}

Contact verification is designed to prevent man-in-the-middle attacks:

\begin{itemize}
\item \textbf{Public key distribution:} Public keys are obtained through user discovery API, not included in contact requests
\item \textbf{Out-of-band verification:} Users must verify public key fingerprints through external channels (not implemented in this version, but architecture supports it)
\item \textbf{Trust status:} Users can mark contacts as verified after manual fingerprint verification (user-declared, not cryptographically enforced)
\item \textbf{No key rotation:} Current implementation does not support key rotation; future versions may implement it
\end{itemize}

\item \textbf{Queue fallback:} If recipient has no active connections, message is queued in database
\item \textbf{Offline notification:} When users come online, message queue service automatically delivers queued messages
\item \textbf{Delivery confirmation:} Senders receive confirmation when messages are delivered or queued
\end{itemize}

\begin{itemize}

\item \textbf{message\_delivered:} Recipient confirms message receipt
\item \textbf{message\_read:} Recipient indicates message has been read
\item \textbf{presence\_update:} User changes presence status
\item \textbf{user\_online/user\_offline:} Presence notifications to contacts
\item \textbf{ping/pong:} Connection keep-alive
\end{itemize}

\section{Core Implementation Flows}

\subsection{Registration and Authentication Flow}

The registration process begins when a user submits the registration form. The client validates username and password format before sending a request to \texttt{/api/auth/register}. The server performs additional validation including username uniqueness checking. Upon successful validation, the password is hashed using bcrypt with a work factor of 12, and an account record is created in the database.

Following account creation, the client generates an Ed25519 key pair using TweetNaCl's \texttt{keyPair()} function. The private key is encrypted using a user-provided passphrase through NaCl's secretbox primitive (symmetric encryption). The encrypted private key is stored in the browser's sessionStorage, while the public key is uploaded to the server via \texttt{/api/auth/crypto/upload-key}. The server creates a cryptographic profile linked to the account, storing only the public key.

If the user chooses to enable cloud backup, the encrypted private key (still encrypted with the passphrase) is sent to the server via \texttt{/api/auth/crypto/enable-backup}. The server stores this encrypted backup but cannot decrypt it without the user's passphrase.

The login flow begins with username and password authentication via \texttt{/api/auth/login}. Upon successful password verification, the server creates an account session token (32 random bytes hex-encoded) and stores it in the database with a 24-hour expiration. The client stores this token for subsequent authenticated requests.

To establish a cryptographic session, the client requests a challenge via \texttt{/api/auth/crypto/challenge}. The server generates a random 64-character hexadecimal challenge and stores it with a 5-minute expiration and binding to both the account session and crypto profile. The client signs this challenge using the Ed25519 private key (retrieved from sessionStorage and decrypted with the passphrase) and sends the signature to the server via \texttt{/api/auth/crypto/verify}. The server verifies the signature using TweetNaCl's \texttt{sign.detached.verify()} function with the stored public key. Upon successful verification, a cryptographic session token is created with a 24-hour expiration.

\subsection{Secure Messaging Flow}

When a user types a message and sends it, the client first ensures both account and cryptographic sessions are active. The client retrieves the recipient's public key (obtained during contact establishment). Since Ed25519 keys are used for signing but Curve25519 is needed for encryption, the client uses the ed2curve library to convert the recipient's Ed25519 public key to a Curve25519 public key.

The client also converts its own Ed25519 private key (secret key) to a Curve25519 secret key by extracting the seed (first 32 bytes) and using ed2curve's \texttt{convertSecretKey()} function.

A random 24-byte nonce is generated for the message. The plaintext message is encrypted using NaCl's \texttt{box()} function, which performs authenticated encryption using Curve25519 key exchange and ChaCha20-Poly1305. The encrypted payload is structured as a JSON object containing the base64-encoded nonce and encrypted data.

The client sends this encrypted payload to the server either via WebSocket (for real-time delivery) or HTTP POST to \texttt{/api/messages/send}. The server validates that the sender and recipient are mutual contacts by querying the contacts table. The server stores the encrypted payload in the messages table without attempting to decrypt or validate its contents.

If the recipient is online (has active WebSocket connections), the server immediately broadcasts the message to all of the recipient's connections. If the recipient is offline, the server queues the message in the message\_queue table. The message queue service periodically checks for queued messages and delivers them when recipients come online.

When the recipient's client receives an encrypted message, it decrypts the payload using NaCl's \texttt{box.open()} function with the sender's public key (converted to Curve25519) and the recipient's private key (converted to Curve25519). The decrypted plaintext is then displayed in the chat interface.

\subsection{Contact Management Flow}

Contact management begins with user discovery. A user searches for another user by username via \texttt{GET /api/users/search?q=username}. The server queries the accounts and crypto\_profiles tables to find matching users with active accounts and cryptographic profiles. The response includes usernames and public keys.

To send a contact request, the user calls \texttt{POST /api/contacts/request} with the target username and optional message. The server verifies that both users exist and have crypto profiles, prevents self-contacts, and checks for existing relationships. A contact record is created with status 'pending' and contact\_status 'pending'.

The target user receives a WebSocket notification about the incoming contact request. The user can accept or reject the request via \texttt{POST /api/contacts/:requestId/accept} or \texttt{POST /api/contacts/:requestId/reject}. Upon acceptance, the server updates the contact record to 'accepted' status and creates a reciprocal contact record, establishing a mutual relationship.

Once contacts are mutually accepted, both users can send messages to each other. The contact list is retrieved via \texttt{GET /api/contacts}, which returns contacts with their usernames, public keys, and presence information (online/offline status, last seen timestamp).

\item Database errors: Transaction rollback and error logging without exposing database details
\item WebSocket errors: Connection closure with appropriate close codes and messages

\begin{verbatim}
{
  "error": "ERROR_CODE",
  "message": "Human-readable error message"
}
\end{verbatim}

\subsection{Session Management}

Session management is implemented at two levels:

\textbf{Account Session Management:}
\begin{itemize}
\item Session tokens are 32 random bytes hex-encoded (64 characters)
\item Sessions expire after 24 hours of absolute time or inactivity
\item Session activity is updated on each authenticated request
\item Sessions track IP addresses and user agents for security monitoring
\item Multiple concurrent sessions per account are supported
\item Sessions can be explicitly revoked by logout or administrative action
\end{itemize}

\textbf{Cryptographic Session Management:}
\begin{itemize}
\item Crypto session tokens are 32 random bytes hex-encoded
\item Sessions expire after 24 hours of absolute time (same as account sessions)
\item Crypto sessions require active account sessions (hierarchical dependency)
\item Session activity is updated on each crypto operation
\item Failed challenge verification does not create crypto sessions
\item Crypto sessions are automatically invalidated when account sessions expire
\end{itemize}

\textbf{WebSocket Session Management:}
\begin{itemize}
\item WebSocket connections require both account and crypto session tokens
\item Connections are validated before upgrade from HTTP to WebSocket
\item Connection manager tracks active connections per user
\item Users can have multiple WebSocket connections (multiple browser tabs)
\item Dead connections are detected through ping/pong heartbeat mechanism
\item Connection close automatically updates user presence to offline
\end{itemize}

\section{Design Trade-offs and Technical Decisions}

Several design decisions involved trade-offs between security, usability, and implementation complexity:

\textbf{Single Key Pair for Signing and Encryption:}
\begin{itemize}
\item \textbf{Decision:} Use Ed25519 for signing with conversion to Curve25519 for encryption
\item \textbf{Rationale:} Reduces key management complexity while maintaining security
\item \textbf{Trade-off:} Less separation of concerns than separate key pairs, but acceptable for this use case
\end{itemize}

\textbf{Session Duration:}
\begin{itemize}
\item \textbf{Decision:} 24-hour account sessions, 24-hour crypto sessions
\item \textbf{Rationale:} Balance between security and usability by maintaining consistent session duration across both layers
\item \textbf{Trade-off:} Longer crypto sessions improve user experience while maintaining cryptographic authentication requirements
\end{itemize}

\textbf{WebSocket Over HTTP Polling:}
\begin{itemize}
\item \textbf{Decision:} Use WebSocket for real-time communication instead of HTTP polling
\item \textbf{Rationale:} Lower latency, reduced server load, bidirectional communication
\item \textbf{Trade-off:} WebSocket requires connection management complexity, but provides better user experience
\end{itemize}

\textbf{Soft Delete for Messages:}
\begin{itemize}
\item \textbf{Decision:} Implement soft delete (deleted\_by\_sender, deleted\_by\_recipient flags) instead of hard delete
\item \textbf{Rationale:} Maintains delivery guarantees and allows recovery from accidental deletion
\item \textbf{Trade-off:} Messages remain in database, but enables better data integrity
\end{itemize}

\textbf{No Forward Secrecy:}
\begin{itemize}
\item \textbf{Decision:} Use long-term key pairs without ephemeral keys for forward secrecy
\item \textbf{Rationale:} Simplifies key management and reduces implementation complexity
\item \textbf{Trade-off:} Compromised long-term keys can decrypt all historical messages, but acceptable for initial implementation
\end{itemize}

\textbf{Client-Side Encryption:}
\begin{itemize}
\item \textbf{Decision:} All encryption occurs in browser using JavaScript
\item \textbf{Rationale:} Zero-trust principle requires no server access to plaintext
\item \textbf{Trade-off:} Depends on browser security and client-side JavaScript, but essential for privacy guarantees
\end{itemize}

\section{Known Issues and Resolutions}

Several issues were encountered during development and testing, with resolutions documented below.

\textbf{Issue: WebSocket Authentication Failure on Page Refresh}
\begin{itemize}
\item \textbf{Problem:} WebSocket connections failed to authenticate after page refresh, requiring manual reconnection
\item \textbf{Root Cause:} Session tokens were not persisted in sessionStorage, causing loss on refresh
\item \textbf{Resolution:} Modified client to store both account and crypto session tokens in sessionStorage, restoring on page load and automatically re-establishing WebSocket connections
\end{itemize}

\textbf{Issue: Cryptographic Session Expiration During Long Idle Periods}
\begin{itemize}
\item \textbf{Problem:} Users were unexpectedly logged out during message composition after crypto session expiration
\item \textbf{Root Cause:} Crypto sessions expire after 24 hours, but UI did not notify users before expiration
\item \textbf{Resolution:} Implemented automatic crypto session renewal when sending messages if session is near expiration, with user notification if renewal fails
\end{itemize}

\textbf{Issue: Message Queue Not Processing After Server Restart}
\begin{itemize}
\item \textbf{Problem:} Queued messages were not delivered after server restart
\item \textbf{Root Cause:} Message queue service was not properly initialized on server startup
\item \textbf{Resolution:} Modified server startup sequence to ensure database initialization completes before message queue service starts, and added health checks for queue service status
\end{itemize}

\textbf{Issue: Race Condition in Contact Request Acceptance}
\begin{itemize}
\item \textbf{Problem:} Simultaneous contact requests between two users could create duplicate contact records
\item \textbf{Root Cause:} Contact creation did not check for reverse relationships atomically
\item \textbf{Resolution:} Added database function \texttt{get\_contact\_status()} and atomic checks before contact creation, with UNIQUE constraint on contact pairs as safety measure
\end{itemize}

\textbf{Issue: Memory Leak in WebSocket Connection Manager}
\begin{itemize}
\item \textbf{Problem:} Server memory usage increased over time with connection count
\item \textbf{Root Cause:} Closed WebSocket connections were not properly removed from connection registry
\item \textbf{Resolution:} Implemented proper cleanup in connection close handlers and periodic cleanup interval to remove stale connections
\end{itemize}

\section{Overall Assessment}

The VoidLink project successfully demonstrates the feasibility of implementing a zero-trust secure messaging system where privacy is mathematically enforced rather than policy-dependent. The two-layer authentication architecture provides a robust separation between account management and cryptographic operations, ensuring that even if one layer is compromised, the other remains secure. The implementation validates the core design principles: end-to-end encryption, client-side key management, and server-side opacity to message contents.

The system achieves its primary objectives of implementing end-to-end encryption with cryptographic authentication, real-time messaging with WebSocket infrastructure, and contact management for secure communication. The architectural decisions, such as using Ed25519 for signatures with conversion to Curve25519 for encryption, provide a balance between security and implementation complexity while maintaining the zero-trust principle.

Performance characteristics observed during development and testing indicate that the system can handle moderate concurrent user loads efficiently, with API response times under 500ms and WebSocket message delivery under 100ms for online users. The message queue system ensures reliable delivery for offline users, demonstrating proper handling of asynchronous communication patterns.

\section{Achieved Objectives}

The project successfully achieved its primary objectives:

\begin{enumerate}
\item \textbf{Two-layer security architecture:} Implemented with clear separation between account sessions (24-hour validity) and cryptographic sessions (24-hour validity), providing defense-in-depth against various attack vectors.

\item \textbf{End-to-end encryption:} All message contents are encrypted client-side using Curve25519 before transmission. The server never has access to decryption keys or plaintext messages, validating the zero-trust principle.

\item \textbf{Cryptographic authentication:} Challenge-response authentication using Ed25519 digital signatures eliminates password-based authentication for message operations, providing cryptographic proof of private key possession.

\item \textbf{Real-time messaging:} WebSocket-based infrastructure enables instant message delivery with bidirectional communication, typing indicators, delivery confirmations, and presence updates.

\item \textbf{Contact management:} Complete contact request, acceptance, and management system enables secure discovery and verification of communication partners.

\item \textbf{Production-ready prototype:} The system demonstrates complete workflow from user registration through secure message exchange, validating the architectural approach and design decisions.
\end{enumerate}

\section{Limitations}

Several limitations exist in the current implementation, acknowledging the scope and constraints of this project:

\begin{itemize}
\item \textbf{No forward secrecy:} The system uses long-term key pairs without ephemeral keys. If a private key is compromised, all historical messages encrypted with that key can be decrypted. Future implementations should consider forward secrecy through ephemeral keys or key rotation.

\item \textbf{No key rotation:} Once a cryptographic profile is created, key rotation is not supported. Users cannot update their keys without creating new accounts. This limitation affects long-term security as keys age.

\item \textbf{Single-device limitation:} The system is designed for single-device use. While cloud backup enables manual key export/import across devices, true multi-device synchronization requires additional complexity in key management.

\item \textbf{Metadata exposure:} While message contents are encrypted, metadata (sender, recipient, timestamps) is visible to the server. Traffic analysis could reveal communication patterns even without access to message contents.

\item \textbf{No group messaging:} The system only supports one-on-one conversations. Group messaging introduces additional cryptographic complexity (group key management, forward secrecy in groups) that is outside the scope of this implementation.

\item \textbf{No file transfer:} While the architecture conceptually supports file transfer, only text messaging is implemented. File transfer would require additional considerations for encryption of large files and efficient storage/transmission.

\item \textbf{Client-side security dependency:} The system's security depends on client-side JavaScript execution in browsers. Browser vulnerabilities, malware, or compromised devices can compromise security. Users must trust their browsers and devices.

\item \textbf{No out-of-band key verification:} While the architecture supports key fingerprint verification, no user interface is provided for out-of-band verification. Users must manually verify keys through external channels.

\item \textbf{Limited testing coverage:} The system relies primarily on end-to-end testing through browser automation. Unit tests for cryptographic operations and integration tests for API endpoints are not implemented, limiting the ability to isolate and test individual components.

\item \textbf{No message expiration:} Messages persist indefinitely in the database. No automatic expiration or deletion mechanism is implemented, potentially raising privacy concerns over time.
\end{itemize}

The VoidLink project successfully demonstrates the feasibility of building a zero-trust secure messaging system where privacy is mathematically enforced rather than policy-dependent. The implementation validates the core architectural principles: two-layer authentication, client-side encryption, and server-side opacity to message contents.

While the current implementation has limitations and areas for improvement, it establishes a solid foundation for further development. The architectural decisions provide a balance between security, usability, and implementation complexity.

The limitations identified, such as lack of forward secrecy and key rotation, point toward important areas for future work. The suggested improvements and future extensions provide a roadmap for evolving the system into a production-ready platform.

Most importantly, the project demonstrates that zero-trust messaging systems are not merely theoretical but can be practically implemented using modern web technologies. The separation of concerns between account management and cryptographic operations, the use of proven cryptographic libraries, and the emphasis on server-side opacity create a foundation where users can have genuine cryptographic guarantees about their privacy, rather than relying solely on service provider promises.
